## 本轮发现并修复的问题

### 教学状态文件没有跟随 Graph

统一 runner 会通过 CLI 推进 Graph，却一直保留初始化时的 `STATUS.md`。例如 Route 课程的 Graph active node 已是 `decision-route`，STATUS 仍写 `intake-root`。这会让学生误以为协议本身发生冲突，也会削弱跨会话恢复教学。

修复后，runner 在课程准备结束时从最终 Graph 重建 STATUS 投影，写入 active node、kind、status、revision、摘要和该课程的下一步。新增回归测试检查 Route 的 STATUS 与 revision 5 一致。

### Review 脚本写入本机绝对路径

三个真实 review 线程都把当前 Codex cache 路径和项目绝对路径写进 `run_review.sh`。Graph 没有泄露路径，但脚本无法在另一台机器、WSL 或不同 Codex 主目录中直接复用。

技能规范现要求脚本从 `BASH_SOURCE` 推导项目根目录，通过 `PYTHON_BIN`、`DS_LITE_EVIDENCE_CLI` 或 `DS_LITE_PLUGIN_ROOT` 解析运行时；本机绝对路径只能在执行时作为环境变量提供，不能写进项目脚本。Experiment 技能同步采用同一规则。

## 尚未解决的风险

### 本地 marketplace 注册不等于插件已安装

`codex plugin marketplace add` 成功把隔离 marketplace 写入配置，但新线程仍加载普通缓存。当前 npm CLI `0.128.0` 只暴露 `plugin marketplace`，没有技能文档所述的 `plugin add/list`；本地 marketplace 的 `upgrade` 又只接受 Git marketplace。因而本轮无法用无界面命令完成 acceptance 包安装。

这不是 cachebuster 生成失败：隔离 manifest、插件 validator 和六个 skill validator 都已通过。发布前仍需在支持本地插件安装的 Codex 版本或插件 UI 中完成一次明确安装，再由新线程核对 cachebuster 版本和 UI 文案。

### 失败证据与 Graph strict 的含义

三分支项目保留 A 的真实阈值失败，因此 `validate --strict` 返回 false、0 errors、1 warning。这里的 false 表示“全图包含未严格通过的实验”，不是 Graph 结构损坏。不能为了得到绿色退出码而删除 A 或改写其 Evidence Pack。审核报告和教学讲义应把“结构有效”与“所有实验均通过”分开表达。

### Codex 线程基础设施错误

主流程 experiment 已完成后，原线程一次、新建线程两次都在 review 开始前出现 `systemError`。三次均没有 agent 输出或文件变更。相同 review 技能此前已在 clean/tampered/threshold-miss 三个线程正常执行，因此现有证据更支持线程服务或调度故障，而不是 review 逻辑错误。仍需在基础设施恢复后重跑主路线下游 Gate。

## 自我反思

1. 最初把“marketplace add 成功”理解成“插件会在重启后安装”，证据不够。真正可靠的判据应是新线程报告的版本、来源和 UI 文案，而不是配置文件里出现了 marketplace 条目。
2. 自动测试验证了 runner 产物和 Graph，却没有检查 STATUS 与最终 active node 一致。课程恰恰要求学生比较这些文件，因此这里的测试空白比普通文案问题更严重。
3. Skill 写着“保存完整命令”，但没有明确“完整不等于硬编码本机路径”。真实触发比静态 validator 更容易暴露这种可移植性缺陷。
4. 分支 Gate 中 strict false 是诚实保存失败证据的结果。审核时不能把所有非零退出码都归为实现失败，也不能为了追求绿色矩阵而抹掉负结果。
5. 独立 Codex 线程能验证技能行为，但仍受宿主线程服务影响。它不能替代非维护者安装、真实课堂反馈或不同机器上的缓存升级证据。
