# v0.3 硬化记录

这份记录按阶段说明 v0.3 人工验收之后的原则性修正。它记录可复用的设计决定、实际验证和仍未关闭的风险，不把临时终端输出或机器路径写进长期文档。

## 阶段 1：隔离的 Codex 验收工具

### 问题

此前的人工步骤容易把“添加 marketplace 来源”和“插件已经安装”混为一谈，也依赖维护者手工复制目录、修改版本和准备教学现场。这样既不容易复核，也可能误碰已有缓存。

### 决定与实现

- `prepare_codex_acceptance.py` 只创建全新的隔离目录：复制插件、添加仅用于验收的 build metadata、生成唯一 marketplace 名称，并准备确定性 student fixture。
- `audit_codex_acceptance.py` 检查 manifest、marketplace 路径、六个技能和 fixture 边界；宿主探测只运行只读命令，不以 marketplace 存在推断安装成功。
- Bash 和 PowerShell 包装都支持 `PYTHON_BIN`，从脚本位置推导仓库根目录，并拒绝覆盖已有输出。
- 验收记录采用 `ds-lite.codex-acceptance.v1` 和 `ds-lite.codex-acceptance-audit.v1`。安装、技能发现和真实线程结果保持为独立字段；自动化工具不会替人工证据填成通过。

### 验证

- 标准库单元测试覆盖中文与空格路径、完整 fixture、重复输出拒绝、版本不一致检测，以及“结构通过但安装仍未验证”的状态。
- 仓库验证器检查验收工具、包装脚本和本记录存在，并对 Python 文件做语法检查。

### 尚未关闭

- 不同 Codex 构建暴露的插件浏览界面可能不同。工具只探测 CLI 的 marketplace 能力；最终安装和六技能发现仍须在新会话中确认。
- 线程无输出或宿主 `systemError` 属于宿主基础设施证据，不能由仓库内脚本证明已经修复。

## 阶段 2：可移植运行脚本

### 问题

初始化生成的四个脚本此前只是提示文字。真实技能触发时，代理容易从当前会话复制插件 cache 和项目绝对路径，脚本离开本机便失效。

### 决定与实现

- 新增项目内共享运行时 `tools/ds_lite_runtime.sh`，统一解析 Python、状态 CLI 和 Evidence CLI；四个入口不再各自复制探测代码。
- 项目根目录只从入口脚本的 `BASH_SOURCE` 推导。CLI 可由专用环境变量或 `DS_LITE_PLUGIN_ROOT` 提供；解析失败时给出可执行的错误信息，不扫描 Codex cache。
- `run_research.sh` 是状态 CLI 通用入口，`run_experiment.sh` 透传 Evidence Pack 的 init/finalize/verify，`run_review.sh` 固定执行 strict verify，`run_analysis.sh` 只追踪 progression route。
- Experiment 和 Review 技能必须保留初始化的公共 resolver，只补任务参数和项目命令，不能用本机路径重写整个脚本。

### 验证

- 初始化测试检查五个生成脚本为 LF、没有用户目录/cache/仓库绝对路径，并在 Bash 可用时逐个执行 `bash -n`。
- 代表性回放通过环境变量定位当前插件，在生成项目中执行 `run_research.sh status --json`，验证中文与空格路径可用。

### 尚未关闭

- 脚本只解决运行时发现与协议入口，不能自动推断宿主项目的训练命令、数据挂载或集群调度参数；这些内容仍须由 Experiment 按契约补全。
- Windows 原生 PowerShell 不直接执行 `.sh`；Windows 用户应使用 Git Bash 或 WSL，仓库验证仍保留 PowerShell 入口。

## 阶段 3：当前路线严格校验

### 问题

默认 `validate --strict` 会把全图所有警告升级为失败。分支课程诚实保留 A 的退化和 C 的违规证据后，全图严格检查自然为非零；这不能说明当前选中的 B 路线不可交接，也不应通过删除失败分支来“修绿”。

### 决定与实现

- 保留默认 `--scope all`，避免改变现有 CI 和维护脚本语义。
- 新增 `--scope active-route`：root 到 active 的 progression route 上的警告参与 strict 判定，其他节点警告进入独立的 `off_route_warnings`。
- 所有结构、时间戳、路径完整性、重复边、不可达和环错误仍放在全局 `errors`，任何 scope 都不能绕过。
- JSON 同时报告 `scope`、`active_node_id`、`active_route`、`warnings`、`off_route_warnings` 和全图 `warning_count`，避免“当前路线通过”被误读为“全图没有问题”。
- `run_analysis.sh` 在追踪路线前先执行当前路线 strict gate。

### 验证

- 回归测试构造失败实验 A 和 active idea B：默认 strict 因 A 的缺失 Evidence Pack 返回 1；active-route strict 返回 0，但仍完整报告 A 的警告。
- 仓库 smoke 改用明确的 active-route 发布门；全图语义测试继续覆盖原默认行为。

### 尚未关闭

- progression DAG 若存在多条 root→active 路径，当前路线与 `trace`、Research Map 一样采用确定性找到的第一条路径。若未来需要“所有 active 祖先”语义，应新增独立 scope，不能静默改变当前定义。

## 阶段 4：可核对的状态交接

### 问题

STATUS 只写 active node 是否 blocked，会漏掉“active experiment 的下一个 review 已被阻塞”这种常见状态；分支课程又可能把 A/C 的阻塞误写成 B 当前路线的阻塞。旧 `lab-result.json` 也没有可机器核对的 STATUS 投影。

### 决定与实现

- runner 在最终 Graph 上运行 progression trace，再生成 `ds-lite.teaching-handoff.v1`：active id/kind/status、revision、active route、当前路线阻塞、active 的阻塞后继和保留的非当前路线阻塞。
- `lab-result.json` 同时保留便于旧检查读取的 `status_active_node` 与 `status_revision`。
- STATUS 将三类 blocker 分行书写。失败 review 保持 `blocked` 且非 active；experiment 或明确补救节点继续 active，使“不能提升结论”和“下一步仍可操作”同时成立。
- runner 仍只写自己刚创建的新项目，不接管普通用户项目的 STATUS。

### 验证

- 六类课程的现有 student/reference 测试统一核对 Graph、STATUS 和 handoff revision/active id。
- 新增 threshold-miss reference 回归：review blocked、experiment active、无 analysis，STATUS 明确列出 blocked review。
- 三分支 reference 核对 A 的失败 experiment 及 A/C review 位于 `off_route_blockers`，B analysis 仍是 active。

### 尚未关闭

- STATUS 仍是面向人的投影，不和 graph.json 组成跨文件数据库事务；恢复时必须以 Graph 为机器权威来源，并核对 revision。

### 复验中暴露并修复的问题

PowerShell 最初把 `codex.ps1` 交给 Python 直接执行，触发 WinError 193。修复后，包装脚本只选择 PowerShell 识别为 Application 的启动器；审计器也会把不可执行文件记录为 `unavailable`，而不是异常退出。Git Bash 下不自动把 MSYS 路径交给 Windows Python 探测，安装状态继续作为人工门。

当前宿主的 `codex-cli 0.128.0` 支持版本查询，但不支持 `plugin marketplace list`。审计结果因此是 `package_valid: true`、`host_supported: false`、`installation_verified: false`。这三个字段必须分别解释，不能合并成一个“验收通过”。

### 当前判断

代码、模板、教学状态和本地跨 shell 验证已经闭环；当前机器没有形成修复后的 WSL DrvFS/ext4 证据，Codex cachebuster 安装、六技能新会话发现和远程矩阵也仍是独立门。Draft PR 应继续保持 Draft。
