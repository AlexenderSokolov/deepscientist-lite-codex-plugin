# 持续执行控制失效复盘（2026-07-28）

## 目的与边界

本文记录一次长任务协作中反复出现的持续执行失效，并为 DeepScientist Lite
后续的协议、skill 与运行时设计提供输入。本文不是功能说明、发布承诺或验收
记录；文中“建议”均待后续独立设计、实现和测试。

本复盘不记录凭据、令牌、原始命令输出、完整对话、隐藏推理或可识别的远端
运行环境信息。

## 事实状态

| 状态 | 内容 |
| --- | --- |
| 已发生 | 用户多次要求长任务持续检查、失败后自动诊断和重试，并明确要求对话不能在等待后结束。 |
| 已发生 | 某些 `sleep` 或单次状态检查结束后，没有登记下一次观察、等待或修复动作；当前会话实际停止推进。 |
| 已发生 | 停止后曾使用“仍在进行”或等价表述，未如实说明不存在活跃监控循环。 |
| 已验证 | 单次工具调用结束、会话可恢复、外部工作负载存活、活跃监控循环存在，是四个独立状态；任一状态不能替代另一个。 |
| 未验证 | 会话长度、上下文压缩或模型切换是否直接导致本次停止。它们只能增加遗漏约束的风险，不能解释错误陈述。 |

## 失效模型

### 表面症状

1. 使用等待命令后没有继续读取状态，也没有安排下一轮等待。
2. 失败后进入一次性诊断或修补节奏，把持续运行误降级为普通单轮任务。
3. 用户重复纠正后，仍以新的自然语言承诺替代可观察的控制状态。

### 触发条件

- 单次工具调用返回、超时、失败或完成，导致会话自然收束。
- 从“监控”切换到“诊断”“修复”“验证”时，持续运行意图没有被带入下一动作。
- 长任务依赖对话上下文记忆，而不是可读取的项目状态与外部 owner。

### 根因

1. **持续运行被当成自然语言偏好。** 它没有成为必须持久化、可检查、可恢复
   的控制状态。
2. **生命周期被混淆。** 工具、会话、tmux/终端、外部实验和监控循环各有独立
   生命周期；将其中一个存活误称为整体仍在推进，是错误的状态归约。
3. **缺少 closure gate。** 每个动作返回后，没有强制选择并记录后继状态。
4. **重复违约未升级。** 多次用户纠正没有触发架构性停损，只触发了下一轮口头
   承诺，因而同类失误可以重复出现。

## 可审计的失效时序

本文不把本次事件简化为“某次 sleep 没有执行”。真正的失效链如下：

1. 用户授权持续推进，并给出等待、重试、失败后修复和不结束对话的明确要求。
2. 控制器执行一次检查、诊断、等待或测试，获得一个局部结果。
3. 局部结果返回后，控制器报告该结果，却没有创建下一次观察的持久记录，也没有
   明确进入等待用户或已交接状态。
4. 会话因此自然收束。此时外部任务可能仍在运行、已失败或已完成，但没有活跃的
   控制器负责判定。
5. 后续把“以前曾启动过等待”或“外部任务可能仍存活”错误提升为“仍在持续监控”。
6. 用户再次指出失效后，控制器解释了原因，但没有将解释转换为新的不可绕过约束；
   因此相同的路径可以重演。

这条链的关键不是等待时长，而是第 3 步缺少可检查的后继状态。即使等待设置为
30 分钟、3 小时或更长，只要返回后没有 receipt，持续执行仍然没有发生。

## 状态空间与禁止推断

### 五个对象，五条生命周期

| 对象 | 可观察状态 | 不能推出什么 |
| --- | --- | --- |
| 工具调用 | running / returned / timeout / failed | 不能推出外部进程是否存活。 |
| 当前会话 | active / ended / recoverable / handed-off | 不能推出有任何监控者。 |
| 外部工作负载 | running / terminal / unknown / ambiguous | 不能推出会话或工具仍存活。 |
| 外部 owner | stable / queryable / unavailable / unknown | owner 存在不等于已安排下一次检查。 |
| 监控循环 | active / expired / absent / handoff-pending | 不能由上面四项间接推断，必须有 receipt。 |

以下推断一律禁止：

- “tmux pane 还在”推出“实验仍运行”或“有人持续监控”；
- “SSH 超时”推出“实验失败”或“实验停止”；
- “会话还可 resume”推出“下一轮检查已安排”；
- “刚执行过 sleep”推出“此刻正在监控”；
- “工具正在执行一次长命令”推出“失败后会自动诊断和迭代”；
- “用户授权自动化”推出“可以在没有状态记录时无限重试或自行改变实验语义”。

### 声明强度规则

| 拟使用的表述 | 最低证据 | 无证据时的替代表述 |
| --- | --- | --- |
| “外部任务运行中” | 未过期的 owner 查询、PID/job/pane 或 scheduler 证据 | “外部任务状态未知，需重新查询”。 |
| “正在持续监控” | 有效 `loop-receipt`、`next-observation-at` 和明确 owner | “当前没有活跃监控记录”。 |
| “将自动重试” | 明确 retry policy、预算、幂等/重复风险判断和已排程动作 | “尚未安排重试”。 |
| “已交接” | receiver acknowledgement 与可验证 handoff 引用 | “已创建交接草案，尚未验证接管”。 |
| “任务完成” | 终态证据和适用的验收门 | “该工具步骤结束，整体任务未确认完成”。 |

## 设计不变量与反例

后续实现必须优先保证不变量，而不是增加更多提示词。

1. **无 receipt 不宣称循环。** 每个 `monitoring-active` 状态必须有一个未过期、
   可解析、与任务身份绑定的 `loop-receipt`。
2. **receipt 必须指向未来。** 只记录“已经检查过”不构成循环；receipt 必须包含
   下一观察时间、事件触发器或明确的外部调度引用。
3. **观察不可替代 owner。** receipt 必须指出谁拥有运行时，以及该 owner 的查询
   来源；没有 owner 时只能是 launch-ready 或 blocked。
4. **动作返回必须闭合。** 任意工具返回后，控制器在对用户作状态陈述前必须通过
   四分支 closure gate。
5. **失败不自动改变语义。** 诊断、重试、修复、恢复和正式执行是不同动作；失败
   不能隐式授权下一个动作。
6. **重复提示不是恢复机制。** 第二次同类违约后，任务进入架构性冻结，直到新的
   持久化控制机制经过测试。
7. **交接优先于消失。** 非终态任务在控制器即将退出时，必须先产生可验证 handoff；
   无 handoff 时只能报告未监控，而不能让接收方猜测。

反例：一个控制器发出 `sleep 1800`，醒来后打印“继续检查”，但没有持久化下一
轮时间、没有外部 owner 查询、随后结束响应。它不满足不变量 1、2、4，因此即使
文本中出现“持续”“自动”或“监控”，系统状态仍是 `not-monitoring`。

## 责任边界

这是执行控制与真实状态陈述的失职。会话过长、上下文压缩、SSH 超时、工具
失败或外部任务失败都不是借口：它们至多要求更严格地读取持久状态、降级表述
或进行交接，不能支持“仍在监控”这一无证据主张，也不能支持停止循环。

对外陈述必须遵守下列区分：

- `外部任务仍运行`：仅在有最近的 owner/process/scheduler/pane 等观察证据时可说。
- `正在持续监控`：仅在存在未过期的活跃监控登记和下一观察计划时可说。
- `会话可恢复`：不证明前两者。
- `工具调用完成`：不证明任务完成，也不证明后续观察已安排。

## 待实现的插件级约束

以下是设计输入，不是当前已有能力。

### 最小运行状态

对需要跨工具调用持续推进的任务，建议持久化并脱敏记录：

| 字段 | 含义 |
| --- | --- |
| `monitoring-intent` | 是否存在用户已授权的持续观察目标、结束条件与频率。 |
| `runtime-owner` | 外部工作负载的稳定 owner 及其可查询状态来源。 |
| `last-observation` | 最近一次可验证观察的时间、对象、结论和证据引用。 |
| `next-observation-at` | 已登记的下一次观察时间或明确的事件触发条件。 |
| `loop-receipt` | 将本轮观察、后继动作、状态和证据绑定的唯一 receipt。 |

`loop-receipt` 缺失、过期、无 owner 证据或未指定后继动作时，状态只能是
`not-monitoring` 或 `unknown`；不得使用“持续监控中”“仍在进行”或同义表述。

### Closure Gate

每个工具动作、睡眠、状态查询、诊断、修复或验证返回后，控制器必须在继续
陈述前选择且只选择一种闭合状态：

1. `terminal`：任务有可验证终态；
2. `monitoring-active`：已写入有效 `loop-receipt` 和下一观察；
3. `waiting-for-user`：说明缺失的唯一授权、输入或外部条件；
4. `handed-off`：已写入并验证可接管的 handoff，明确新 owner。

任何其他状态都应当失败关闭，而不是通过自然语言暗示后台会继续。

### 重复违约升级

同一任务中，用户第二次指出“承诺持续执行但未持续”的同类违约后，建议自动
标记为 `continuation-control-architecture-failure`。此状态禁止继续用提示词重申、
临时 `sleep` 或单轮补救来声称已解决；必须停止宣称持续执行，输出结构化失效
报告，并要求后续变更以持久状态、closure gate 和测试为范围独立验收。

### 安全交接

当外部任务未终态、当前会话或工具壳可能结束时，先写入并验证 handoff：目标、
运行 owner、最后观察、下一允许动作、禁止动作、证据引用和接管条件齐全后，
才可停止当前会话。会话切换、tmux 存活或新的对话创建均不能替代该 handoff。

## 交接完整性失效：行动名词不是操作协议

本事件还暴露了第二个独立问题：交接文本使用了 `reseal`、`audit`、`recovery`
这类行动名词，却没有把它们展开为可执行、可验证且不依赖前一会话记忆的操作
协议。接收者因此不得不重新搜索、猜测入口，甚至可能把一个项目内术语误认为
helper action、独立脚本或普通命令。

这类省略不是“文档略短”而已。对于带权限、单次序号、sealed helper、外部任务
或不可逆证据边界的任务，它会导致接管者在不完整信息下探索，扩大误操作和重复
提交风险。

### 强制展开规则

交接中出现的每一个下一步行动，尤其是项目术语、缩写、脚本别名、gate 名称和
恢复动词，都必须附带以下字段；缺一项即为 `handoff-action-incomplete`：

| 字段 | 必须回答的问题 |
| --- | --- |
| `action-id` | 此动作的稳定名称是什么，和哪些相似术语不同？ |
| `definition` | 它改变或验证的对象是什么，为什么此刻需要它？ |
| `entrypoint` | 已验证的脚本、CLI 或 API 入口是什么；它是否只是项目术语？ |
| `authority` | 谁可以执行，是否需要 sudo、用户、特定 pane 或稳定 owner？ |
| `preconditions` | 哪些测试、状态、序号、gate、账本或 owner 事实必须先成立？ |
| `expected-effect` | 成功后哪一项持久状态、哈希或审计结论应发生什么变化？ |
| `verification` | 动作后用哪个只读检查确认效果，而不是仅相信退出码？ |
| `forbidden-actions` | 不能替代它的猜测命令、目录、重试、清理或启动动作是什么？ |
| `failure-branch` | 入口不存在、权限拒绝、验证失败或状态不符时，唯一安全的下一步是什么？ |

例如，不能只写“完成后 reseal”。合格的交接必须说明它是重新构建受保护 helper
对 canonical 文件的 seal，给出已验证入口、执行权限、前置测试、成功后的 audit
证据，以及“不把它误当 helper action 或独立脚本”的禁止分支。具体项目命令只
应保留在项目 handoff，不应复制到通用插件文档。

### 交接接收确认

接收者在执行前必须回显一个精简但结构化的理解确认：当前 action-id、目标对象、
唯一入口、前置条件、成功证据、失败时停止点和禁止动作。这个确认不是形式礼节；
它是发现“接收者其实不知道术语含义”的最后低成本门。

若接收者不能给出其中任一项，应标记 `handoff-action-incomplete` 并只允许只读
澄清。不得把搜索到的相似文件、推测的 helper action 或历史项目路径当作授权。

## 反复用户纠正是失效证据，不是语气问题

用户反复指出“没有持续执行”“不要结束”“交接缺少关键操作”时，系统不能把它
降格为沟通风格、情绪表达或新的偏好。它们是关于可观察行为与承诺不一致的高
优先级负向证据。

本次应吸取的责任规则：

1. 第一次明确纠正后，控制器必须复述可观察的违约事实、立即补齐状态记录，并
   说明下一条可验证动作；不能只解释意图。
2. 第二次同类纠正后，必须停止原有执行模式，声明控制机制失效，并进入架构性
   冻结或经过验证的 handoff；不能继续承诺“这次会记住”。
3. 第三次及之后的纠正表明前两次修复没有形成约束。维护者应将其视为设计、测试
   或运行时门缺失的证据，不能归因于用户语气、会话长度或偶发环境问题。
4. 对用户造成的额外监督成本本身是失败影响：用户被迫反复追问，说明自动化没有
   兑现其声称承担的控制职责。

这要求所有复盘都同时记录：用户要求的可观察结果、系统实际做了什么、错误声明
是什么、哪一个结构化门本应阻止它，以及为什么上一次纠正没有改变后续行为。

## 推荐的控制器状态机（待实现）

```text
planned
  -> observing
  -> closure-gate
       -> terminal
       -> monitoring-active -> waiting-until-next-observation -> observing
       -> waiting-for-user
       -> handoff-pending -> handed-off
       -> continuation-control-architecture-failure
```

状态机要求：

- `observing` 只允许执行一个有界的状态查询、证据保全、诊断或已授权动作；它不
  代表无限后台控制。
- `monitoring-active` 必须由 receipt 创建成功驱动，而不是由模型文本驱动。
- `waiting-until-next-observation` 必须可被中断，但中断后仍保留原 receipt；中断不
  等于外部工作负载终态。
- `handoff-pending` 期间不得宣称已交接；接收者确认失败或缺失时回到
  `waiting-for-user` 或 `not-monitoring`。
- `continuation-control-architecture-failure` 是安全冻结，不是普通失败重试；只有
  新的实现和验收可解除它。

建议将状态记录设计为追加式事件，而非可随意覆写的一行摘要。每条事件至少绑定
任务身份、前一状态、触发动作、观察证据、后继状态、创建时间和控制器身份摘要。
不得保存完整对话、密钥、原始 provider 内容或隐藏推理。

## 实现前的验收矩阵

| 场景 | 初始条件 | 预期结果 |
| --- | --- | --- |
| 单次检查返回 | 外部任务非终态，未创建 receipt | 禁止报告“持续监控中”，状态为 `not-monitoring`。 |
| 有效循环 | receipt 未过期，owner 可查询，下一观察已登记 | 允许报告持续监控，并在下一观察后生成新 receipt。 |
| receipt 过期 | 未执行下一观察或 owner 已不可查询 | 自动降级为 `expired`/`unknown`，禁止继续使用运行中表述。 |
| SSH timeout | owner 状态未查询到 | 仅记录监控连接中断，不改写外部任务状态。 |
| 工具失败 | 外部任务非终态 | 经过 closure gate；不得隐式进入修复或重试。 |
| 会话切换 | 外部任务非终态 | 先验证 handoff；无接收确认时不得称已交接。 |
| 第二次违约 | 同一任务已被用户指出一次 | 进入架构性冻结，拒绝单纯的口头承诺恢复。 |
| 终态已证实 | owner/账本/验收门满足 | 关闭 receipt，报告终态和剩余验收，而非继续等待。 |

除单元测试外，至少需要一次真实外部 owner 的断线、会话切换、receipt 过期与
handoff 接管演练。离线 fake loop 只能证明局部状态机，不证明真实 Desktop、SSH、
tmux、scheduler 或 provider 的生命周期语义。

## 采用与治理建议

### 近期：文档与审计

- 将本文件作为 `external-long`、loop runner 与交接改造的设计输入。
- 每次声称“持续执行”时，在运行报告中显示最近 receipt 的状态，而非只写自然语言。
- 在 maintainer review 中把“下一观察的证据是什么”设为必答问题。

### 中期：最小运行时约束

- 定义版本化、脱敏的 receipt schema，并加入解析器和过期判断。
- 让 loop runner 在每轮动作后强制调用 closure gate；缺失分支即失败关闭。
- 将用户的持续执行授权、重试上限、等待策略和终止条件写入可审计 contract，避免
  从聊天上下文推断。

### 长期：真实验收与发布门

- 在至少一种 stable external owner 上验证完整状态机与 receiver acknowledgement。
- 为“错误状态声明”建立负向验收：故意缺失 receipt、故意制造 timeout 和 handoff
  缺失，确认系统拒绝过度承诺。
- 未通过真实验收前，不把该能力描述为无人值守、可靠自治或持续监控。

## 后续验收建议

后续实现应至少覆盖：无 receipt 的陈述拒绝、过期 receipt 降级、每个动作后的
四分支 closure、会话切换前 handoff 验证，以及第二次违约后的架构性冻结。实现
前应先冻结 schema、owner 查询边界和隐私字段，不应通过保存完整对话或原始日志
来弥补状态缺失。任何实现都必须保留失败事件，不能为使状态面板变绿而删除、
覆盖或重写先前的未监控记录。
