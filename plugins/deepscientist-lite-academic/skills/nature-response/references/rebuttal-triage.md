# Rebuttal triage and evidence gate

This is an original DS Lite procedure based on general review-response
practice. `TobiasLee/Rebuttal-Skill` was considered as a requirements signal;
because no repository-root license was observed during planning, no upstream
wording or file is copied here.

## Gate 1: Is rebuttal work worthwhile?

Classify the decision, deadline, venue rules, reviewer overlap, available
evidence, experiment cost, and probability that a response can change the
outcome. If the expected return is low, produce a triage note instead of an
inflated response package. Separate appeal, revision, and resubmission.

## Gate 2: Atomic concerns

Split every editor or reviewer item into one claim that can receive one of:
`accept`, `clarify`, `revise-text`, `run-experiment`, `decline-with-reason`, or
`needs-author-input`. Shared major concerns receive one canonical concern ID;
reviewer-specific answers cite it instead of duplicating inconsistent plans.

## Gate 3: Experiment priority

- `P0`: required to keep the central claim defensible or satisfy an explicit editor gate.
- `P1`: high-value evidence that materially resolves a major concern.
- `P2`: useful clarification or robustness evidence with bounded cost.
- `P3`: low-return expansion, polish, or work better deferred to resubmission.

Priority is not completion. Each experiment keeps `planned`, `running`,
`positive`, `negative`, `inconclusive`, `blocked`, or `not-run`, plus an
Evidence Pack reference. Negative and inconclusive results must be fed back
without being rewritten as support.

## Gate 4: Package readiness

A response is ready only when every atomic concern has a disposition, every
claimed change has a location, and every claimed experiment has a result
reference. Missing or negative results may require claim reduction. The
resubmission gate records what transfers to a new manuscript and what must not
be represented as completed in the current response.
